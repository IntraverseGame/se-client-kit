# Wrapper

Status: **Draft, for human review.** This is the contract the Wrapper is built
and tested to. It takes effect for the code when the first release lands. The
[questions it raised](#decided-questions) (OQ-1 to OQ-8) are decided: OQ-1 to
OQ-6 by the TPO (the Technical Product Owner) on 2026-10-15, OQ-7 by the TPO on
2026-10-16, and OQ-8 on 2026-10-16 by the backend's player-facing contract; none
is open. The signed-action grammar, `T_0`, and the signing vectors belong to the
backend's signed-action spec and are only referenced here
([What this spec does not own](#what-this-spec-does-not-own)).

## Purpose

- The Wrapper is the part of SuperEngine that runs in the player's browser and
  holds the player's credentials: the play token and the action key. It opens a
  session from a launch code, signs the player's actions, checks what the
  backend tells it about the round, renders the Snapshot, and hosts the game
  iframe.
- The player trusts this code with the one key that can cash out their round. So
  the contract is written as requirements that a test can fail, and the code is
  public ([client-kit.md](./client-kit.md)).
- The first release plays Coin Flip end to end against the SuperEngine backend:
  launch, key setup, round start (the key's address is presented in the `start`
  call; there is no signed `PlayerStart`, W-22), move, and a cash-out (on a
  multi-step game, [OQ-3](#decided-questions)).

## Scope

In scope (first release):

- opening a session from a launch code read from the URL fragment, the play
  token, and its refresh;
- the action key: generation, custody, and what may be stored;
- two tabs of one session (Web Locks);
- the transcript: tracking `T_n`, never signing two actions at one sequence;
- starting a round with the action key's address (no signed start, W-22), and
  signing move, cash-out, and cancel through the signed-action spec;
- verifying the round's `CreateRoundAuth`, and the tip check, before the game is
  shown as ready; `PlayerCancel` when a check fails;
- rendering from the Snapshot, validated against `se.snapshot/1`;
- the round id and the link to the verify page after a round ends;
- the sandboxed game iframe and its `postMessage` controller boundary;
- the single screen: the game frame shown for the whole session over one control
  bar, with a round never shown as ready before the shell's checks pass (decided
  2026-10-30; [The single screen](#the-single-screen), W-57, W-58);
- error states, including network failure;
- accessibility;
- the test plan.

Out of scope:

- native bet controls and controller API variations (later increments). The
  controller boundary below is the minimal first-release one;
- wallet-delegated keys and player-supplied keys;
- WebSocket. The first release uses the REST verbs and polls the Snapshot;
- more than one game at a time; and, of the `playback` presentation, everything
  beyond a book round's base-mode playback with no player input other than the
  start (issue #146, [Book playback](#book-playback), W-50 to W-56);
- the Play API itself and the verify API (backend concerns), and the verify
  page, which the kit builds but which has its own spec,
  [verify-page.md](./verify-page.md).

## Boundary

The Wrapper is the browser side of a contract whose server side the backend
owns.

- **The Wrapper owns:**
  - the player's credentials in the browser: the play token and the action key,
    for the lifetime of the page;
  - the transcript state the player has signed, in the browser;
  - the checks the player makes on the backend's claims: the round's
    `CreateRoundAuth` and the tip check;
  - rendering, and the postMessage boundary toward the game and the operator
    page.
- **The Wrapper does not own:**
  - sessions, tokens, and their validity: it holds a token and never decides
    that one is valid;
  - round state, funding, settlement, and what a Snapshot contains;
  - the signed-action grammar and the verifier;
  - the game's own rendering (the game developer);
  - money: balances and amounts are the operator's, shown as the Snapshot gives
    them.
- **The Wrapper consumes** (contracts, never backend code):
  - the Play API, `/play/v1`, as its OpenAPI document;
  - the Snapshot schema `se.snapshot/1` and its golden vectors;
  - the signed-action spec, followed by name, and its vectors (the signing
    vectors and the `signed-action/` Snapshot vector); (the Play API document,
    the Snapshot schema and vectors, and these vectors arrive as vendored data
    in the kit's `contracts` package, never as backend code);
  - public JSON-RPC endpoints, for the tip check (a local or preview environment
    may use its own node, W-26a);
  - one environment configuration document ([Configuration](#configuration));
  - the operator launch contract, by name only: the launch URL whose fragment
    carries the launch code (W-1).
- **The Wrapper is consumed by:**
  - the player;
  - the operator page, which embeds the Wrapper, completes the `se.operator/1`
    handshake, and receives `welcome` and `resize`; the lobby and the deposit
    are navigations to the Snapshot's `context.links`, not messages
    ([Operator embedding](./wrapper/operator-embedding.md));
  - the game iframe, which receives Snapshots and sends action requests.

How the kit obtains those contracts is in
[client-kit/how-the-kit-gets-its-contracts.md](./client-kit/how-the-kit-gets-its-contracts.md).

### Two tabs

- **W-14.** After the redeem, the shell MUST request an exclusive Web Lock named
  `se:signer:<sessionId>` (`navigator.locks.request` with `ifAvailable: true`)
  and hold it for the page's life. A tab that does not get the lock MUST NOT
  sign, refresh, or poll for the session, and MUST show the "this session is
  open in another tab" state. If the browser has no Web Locks API, the shell
  MUST NOT sign (fail closed).
- **Why it still matters with a memory-only key.** Two tabs cannot share an
  in-memory key, so two tabs of one session do not arise from normal use: a
  second launch is a second session with its own key, and a second redeem of one
  code fails. The lock is the guard that keeps a sequence from forking if a tab
  is cloned or a future design hands a session over. A fork would be
  equivocation by the key holder, and the backend rejects it (a stale `previous`
  or a wrong sequence).

### The transcript

- **W-15.** The shell MUST track, per round it signs for: the round id, the last
  accepted `T` (`T_0` at the start), the next sequence, and the digest, the
  signed bytes, and the `idempotencyKey` of any action it has signed but not
  seen applied. It MUST NEVER sign two different actions for one
  `(round, sequence)`, whatever the network does.
- **W-16.** The shell MUST record a signed action in that state **before** it
  sends it. If the send fails or its outcome is unknown, the shell MUST resend
  the **same signed bytes** with the **same** `idempotencyKey`, or read the
  Snapshot to learn the outcome. It MUST NOT build a new action at that
  sequence. A final answer (a 400 `INVALID_ARGUMENT` or a 409 `STALE_ACTION`,
  W-19) is not a failed send: those bytes are not resent. **A lost move or
  cash-out is resent once** (decided in human review, 2026-10-18): when its send
  was **lost** and a later read of the round (the newest the shell has read of
  it, by `version`: a late, older read decides nothing) shows it not applied
  (the round still `active`, at the step before the action, the action not
  reflected), the shell sends the same signed bytes with the same
  `idempotencyKey` again, once. The resend's answer is what the UI and the game
  are shown, also when the read caused the resend: never the read's older
  Snapshot. A lost send has one definition for every signed action, the cancel
  included (W-25; the start, which is not signed, has its own one resend, W-22):
  no answer, or a 503 not marked `retryable: false` that the transport could not
  get past, a bare 503 with no problem body included (it carries no
  `retryable`). A 503 marked `retryable: false` is never resent, as W-42 reads
  `retryable`: a move or a cash-out settles by a read or by its expiry rule, and
  the cancel keeps reading, since a 503 may come with it stored (W-25). The Play
  API document (since se-backend `075b850`) says that after a lost response,
  `UNAVAILABLE`, or `INTERNAL` the move (or the cash-out) may already have been
  taken, and that the same request (key and signed action) answers the round, so
  resending it is safe. The kit stays more conservative (decided in human
  review, 2026-10-19): after a 500 `INTERNAL`, or a 503 marked
  `retryable: false`, it never resends the move or the cash-out; the action
  stays pending and the reads decide (by a read that shows it applied, or by its
  expiry rule). The one resend after a lost send (no answer, or a 503 not marked
  `retryable: false`) is unchanged. The backend recognises a repeat by its
  signed action (its sequence and bytes) in the round's action log, not by the
  key, which it requires and checks but does not store yet: the same signed
  bytes sent again are answered with the round when they were applied (even once
  the round has closed) and processed normally when they were not, so the shell
  still sends the same key and never re-signs. Another action at an accepted
  sequence is a 409 `STALE_ACTION`, as is a wrong `sequence` or `previous` (the
  Play API document since se-backend `9ffdcc0`); either a 409 or a 400
  `INVALID_ARGUMENT` to a resend is a refusal (W-19), with no further send. The
  one resend is shared by every path: the shell's own after the read and any
  resend the player asks for, so that action is sent at most twice. It never
  re-signs, never sends that action a third time, never resends once a read
  showed it applied, the step moved on, or the round no longer `active`, and
  never in a state that takes no resend (W-19's hold, a failed check, out of
  sync, or the session ended). A re-issue (W-26) does not stop it: the resend is
  not a new signature, so a move or a cash-out already signed is never stranded.
  The cancel flow differs on purpose: after a re-issue it resends nothing
  (W-25). If the resend fails too, the action stays pending, nothing new is
  signed at that sequence, and the round ends as this item says (by a read that
  shows it applied, or by its expiry rule). While the round is still `active`
  with that move or cash-out neither applied nor refused, the Wrapper shows it
  as **not confirmed** (decided in human review, 2026-10-19; the session's
  `RoundState.unconfirmed`), never as a plain round in play: "Your move hasn't
  been confirmed" (or "Your cash-out hasn't been confirmed"), "If it never
  arrives, the round ends by its time limit.", the round id, and "Check again".
  The expiry is text only, with no clock. "Check again" reads the round once (a
  click while that read is in flight does nothing), and the Wrapper reads it
  once every 30 s in the background (W-35); neither ever sends or signs
  anything. A typed error stops the background read, as it stops every poll,
  until the player tries again or checks again: "Check again", like "Try again",
  first clears the typed error shown. The game stays waiting. Any read that
  settles the round clears the state: the move applied shows the result, and the
  step moved on or the round ended follow their usual rules. Only a lost resend
  gives the state: a resend answered with a 503 marked `retryable: false` keeps
  the handling above. A `PlayerCancel` is the exception: the backend does not
  answer a repeated cancel from a log, so the shell sends a cancel again only
  after it read the Snapshot (W-25), never as a blind resend, and only when that
  read showed the round `active` with no move: a read that fails instead puts
  the cancel in settling, and the resend is forgone; after the resend, a second
  unknown outcome and an `active` read with no move put it in settling too, with
  no third send, and so does a re-issued `active` read with no move after an
  unknown outcome (W-25).
- **W-17.** `PlayerCancel` and the first `PlayerAction` of a round are both at
  sequence 1. After the shell signs one, it MUST NOT sign the other for that
  round (signing both is equivocation).
- **W-18.** Sequences start at 1, with `previous = T_0`, and each action's
  `previous` is the `T` of the one before. `T_n` is the struct hash of the
  signed message. The shell advances its `T` only when the response shows the
  action applied, which it knows from the Snapshot's `step` (and `status`), and
  never from a guess. The rule the `shell` package reads from the Snapshot is
  provisional until the signed-action spec ties a sequence to the Snapshot's
  progress ([client-kit.md](./client-kit.md#the-shell-package)). `T_0` is the
  Ready evidence hash, `keccak256(abi.encode(created, seedHash))`, as the
  signed-action specification defines it and the vendored signing vectors
  reproduce; it binds no other input, and a contract version that adds one
  changes `T_0` and its vector. The shell reads its inputs from the Snapshot
  (`proofs.createRoundAuth`, `proofs.fairnessProof`) and recomputes it (W-26,
  check 5).
- **W-19.** A 400 `INVALID_ARGUMENT` or a 409 `STALE_ACTION` to a signed move or
  cash-out is a final answer (decided by human review, 2026-10-17: both codes
  resynchronize alike). The shell MUST NOT resend those signed bytes (the W-16
  resend is only for a lost response or an unknown outcome), MUST hold signing
  for the round, and MUST read the Snapshot before it signs anything else for
  it. It signs again only if the transcript state allows it:
  - it MUST NEVER sign a second action at one `(round, sequence)` (W-15): the
    refused sequence never gets another signature;
  - the shell cannot recompute `T` from a Snapshot, so it never guesses a new
    `previous`: it continues, from the next sequence, only when the Snapshot
    shows its own pending action applied (`T` advances to that action's struct
    hash, W-18). Otherwise it shows the out-of-sync state and offers the verify
    link.

  A 409 falls under the second rule alone. Read as the Play API document defines
  it today, it means another action was accepted at that sequence, so the shell
  never re-signs there and, unless the Snapshot shows its own action applied,
  the round is out of sync. A 422 `FAILED_PRECONDITION` is outside W-19 and
  follows the typed-error table (W-42). The signed-action specification defines
  no other resynchronization rule: a refused action changes nothing (the
  transcript does not advance), and the Wrapper resynchronizes from the
  Snapshot.

### Error and degraded states

- **W-41.** No key, token, or launch code may appear in an error state, a
  notice, the document title, the DOM, the console, or the URL. The error states
  show the typed `code`'s message in the player's language and the problem's
  `requestId`, so support can find the call.
- **W-42.** Typed errors. The Wrapper branches on `code` and never on the
  message; it retries only when `retryable` is `true`, with the same
  `idempotencyKey`, a bounded number of times with backoff, then shows the
  error. The redeem (W-1, W-2) and the cancel (W-25) are never retried
  automatically, whatever `retryable` says. The transport repeats a start (with
  the same `idempotencyKey`) only after a lost response or a `503`
  `UNAVAILABLE`; a start voided or refused before any money moved
  (`FUNDING_UNCONFIRMED`, `ENTROPY_UNAVAILABLE`, `PREPARATION_TIMEOUT`,
  `ROUND_VOIDED`) is sent once whatever its `retryable`, since the Play API
  document says to retry it with a new key, which only the player's new start
  does (W-36). The control the problem shows for these four reads the Snapshot
  again, as "Try again" does, and is labelled "Back to start" (decided by the
  human, 2026-10-20): the read answers `idle`, and the start control is the way
  forward. `UNAVAILABLE` and the other retryable codes keep "Try again". Every
  `code` is one of the schema's closed `ErrorCode` list, so a problem with any
  other `code` fails validation (W-28) and shows the generic error state; for a
  listed `code` this table does not name, it falls back to `status` and
  `retryable` (the "any other" row).

- **W-43.** Network failure. A request that fails with no response (offline,
  DNS, TLS, timeout, reset) MUST show the "connection problem" state without
  losing the round: the Wrapper keeps polling at the slow rate, resends a
  signed-but-unconfirmed action only as W-16 says (a cancel only after a
  Snapshot read, W-25), and says so when the browser reports being offline.
  After the connection returns, it reads the Snapshot first and continues from
  it. A request MUST time out (SHOULD: 15 s, Wrapper configuration). The Wrapper
  never reports success for an action whose outcome it has not read.
- **W-44.** Degraded states the Wrapper MUST show distinctly: session ended;
  open in another tab; connection problem; chain check not independent (W-26a);
  round failed verification; could not verify the chain (W-26a); out of sync
  (W-19); Snapshot rejected (W-28); a changed session (W-53, shown as "this
  round failed verification", and final until a reload). A browser with no Web
  Locks API (W-14) shows its own state too: it signs nothing.

### Accessibility

The Wrapper's own UI (everything except the game's contents) targets **WCAG 2.2
level AA**.

- **W-45.** Every control MUST be operable by keyboard alone, with a visible
  focus indicator and a logical order; the game iframe has a `title`. No
  keyboard trap, including around the iframe.
- **W-46.** A status change MUST be announced to assistive technology through a
  polite live region (`aria-live="polite"`), and an error through
  `role="alert"`. Focus moves to the result or error heading only when the
  player's own action caused the change, never when a poll did, with one
  exception (decided by the human, 2026-10-28; W-55): the poll that brings the
  result of the book round the player just started (its start answered
  `starting`) moves focus to the result heading, once. When the game's iframe
  element has the focus, the Wrapper takes it back for the result or error
  heading by blurring the frame element before focusing the heading, since some
  engines (Firefox with its frames in the parent's process, as in Playwright's
  Firefox build) do not move the focus out of a focused iframe on `focus()`
  alone.
  - **Single screen** (RFC-004, decided 2026-10-30; where it differs from the
    text before it, it holds): the live region reads the bar's status line, or
    the cover's heading for a state on the stage's cover; `role="alert"` is the
    bar's alert line, or the cover when the state is on it
    ([W-57](./wrapper/the-single-screen.md)). When a cover state owns the
    region, a bar error beside it is shown as plain text with no `role`, keeps
    its icon (W-47), and is not announced until the cover's state ends (W-57).
    The result heading is the bar's status heading; the error heading is the
    alert line's or the cover's. The rules above hold, with these:
    - **The inert-frame rule.** An inert frame cannot hold the focus (W-58).
      When the frame becomes inert while it, or its document, holds the focus,
      the Wrapper MUST move the focus, blurring the frame element first, to the
      heading the change calls for under the rules above when there is one, and
      otherwise to the bar's status heading (or the cover's heading), whatever
      caused the change, a poll included, so the focus is never dropped to the
      document's body. It never takes the focus from a control of the bar the
      player is using.
    - **A pick's error keeps the focus in the frame** (decided by the human,
      2026-10-30). When the player's own pick, made in the frame during a
      playable round, is answered by a typed error, the generic error, or a
      connection problem (the frame stays interactive, W-58), the focus is not
      moved: it stays in the frame, and the error is announced through
      `role="alert"`. This is the one case where the player's own action does
      not move the focus to the error heading. A pick whose answer ends the
      round, or makes the frame inert, follows the inert-frame rule.
    - **The removed-control rule.** When the bar's control that holds the focus
      goes away because the state changed (the start control once the start is
      answered, the cash-out control once the cash-out is), the focus moves to
      the bar's status heading.
    - **Into the game** (a second exception to the poll rule, like the book
      round's). When the round the player just started becomes ready (the poll
      that brings the verdict `ready`), the Wrapper focuses the game's iframe
      element, once, for that round only, and only if the focus is on the bar's
      status heading or the body.
    - **Order.** The stage comes first in the tab order, then the bar: its
      status heading (focusable by script only), the alert's control, the
      primary controls, the round line, and the operator links. An inert frame
      has no tab stop. After the result heading takes the focus, the next tab
      stop is the next bet's selector and "Play again".
- **W-47.** Color MUST NOT carry meaning alone (win, loss, and error have text
  and an icon with a text alternative). Text contrast SHOULD be at least 4.5:1
  and the UI SHOULD honor `prefers-reduced-motion` and 200 % zoom without loss
  of function. Targets SHOULD be at least 24 by 24 CSS pixels.
- **W-48.** Every control and state has a text label in the session's `language`
  (the Snapshot's `context.language`), with a fallback language. Money is shown
  as the Snapshot's `formatted` string.

## Security

The key and the token are the assets. What may never happen is in W-3, W-4, W-10
to W-13, W-37, W-38, W-41, and W-49, and is tested by T-9, T-9a, T-13, and T-18.
Summary: the secrets live in one closure in memory, never in storage, a URL, a
log, the DOM, or a message; the game is untrusted, sandboxed on another origin,
and talks only through a closed, origin-checked message set; the operator page
gets its own closed protocol and can unlock the Wrapper, nothing more; the
Wrapper checks the backend's claims (the round's `CreateRoundAuth`, the tip)
before it signs. A listed operator that disguises the Wrapper is a recorded
residual risk with no technical control in the first release
([Operator embedding](./wrapper/operator-embedding.md#security)).

## Observability

The Wrapper emits **no telemetry to the backend in the first release**: no
analytics, no error reporting, no third-party script. No endpoint exists for it
and none is invented here. The player and support work from the problem's
`requestId` shown in the error states (W-41), which the backend already logs.
The Wrapper's console output is `warn` and above, redacted (W-4), and holds no
document. A client-side error channel is a later decision with its own spec.

The session (its open, the token refresh, and the round use cases) logs nothing
and emits no event outside the page: its change and end notices go only to the
Wrapper's own listeners. What the Wrapper logs today, through the shell's
redacting logger, all at `warn`: `config.refused` once per issue of a refused
configuration document, with the issue's `code` only (never a field's value);
`embedding.refused` when a framing is refused (W-49), with its reason `code`
only (never an origin): `ancestor-not-allowed`, `ancestor-masked`,
`ancestors-unknown`, `nested`, `operator-not-allowed`, and `handshake-timeout`
(the table in
[Operator embedding](./wrapper/operator-embedding.md#what-is-logged); one event,
not a second one for the handshake); `config.unreadable`, with the HTTP `status`
when there is one; and `config.unreachable`, with no field.

## What this spec does not own

The signed-action spec belongs to the backend and defines the items below. It is
a separate document, owned and versioned there. This spec restates only the
shell rules it needs and the published values below, and it **defers** to that
spec for everything else.

| Item                                                                        | Where it stands                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| the action grammar (`action` text, `path` encoding, row and tile numbering) | Published. A move is `pick row <r> tile <o>`, a cash-out `cash out`, a cancel `cancel`. Numbers are canonical base-10 (no sign, no leading zero), words are separated by one space, and rows and tiles count from 0 (the Wrapper may show rows from 1, but it signs this form). A move's `path` is the steps survived so far, in order, then the step being played, with `r = len(path) − 1`; a cash-out's `path` is the steps survived; a cancel's is empty. A `path` entry is the step's `config.steps[].index` in the Snapshot; the tile goes only in the text (`tile <o>`), never in the path. Coin Flip's only move is `pick row 0 tile <o>` with path `[0]`; it has one step, so no cash-out ([OQ-3](#decided-questions)). Any other spelling is refused, and a path that does not extend the survived path is refused with 400 `INVALID_ARGUMENT`.                                                                                                                                                                                                                             |
| the EIP-712 domain, the type strings, the type hashes                       | Published. `EIP712Domain(string name,string version,uint256 chainId,address verifyingContract)`, `name` `"SuperEngine"`, `version` `"1"`, and the operator's registry chain and address (pinned in the environment configuration, [OQ-7](#decided-questions)); the round's domain is sealed when the round is committed, and a request never names it. `PlayerAction`, `PlayerCashOut`, and `PlayerCancel` share the fields `(string action,uint8[] path,uint32 sequence,bytes32 round,bytes32 previous)`; their type hashes are `0xb27136af290533abb5d228ae9db36f09654573329adc8928893d2868e17069e9`, `0x4fcc4e30bede285e8cd1551115aee2f18030095285175588103a130a1b118c04`, and `0xacaf7a5ad98f54f1cf2ba32c94a782121894bc4306dbb28b7683c5ef579a9ce6`. `round` is the round id's `bytes32` form (its 16 UUID bytes, left-aligned and zero-padded): the shell reads it from the Snapshot's `proofs.createRoundAuth.newRound.roundId` once W-26 check 3 has matched it to `roundId`, and never takes it from a game request. No signed start exists (W-22, [OQ-5](#decided-questions)). |
| `T_0`: its encoding and where the shell gets its inputs                     | Published: `keccak256(abi.encode(created, seedHash))`, recomputed from the Snapshot's `proofs` (W-18; W-26, check 5).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| the vectors for the above                                                   | `PlayerAction`, `PlayerCashOut`, and `PlayerCancel`: the signing vectors (since contracts release 1.0.0, with a `PlayerCancel` type hash and a `player-cancel` round); `PlayerCancel` also: the independent signer's `signed-action/coinflip-cancel` Snapshot vector (#41). All are vendored in `contracts`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| the `typedData` bytes the Play API passes to the engine                     | The canonical Protocol v1 encoding of `ActionTypedData`, in base64, as the vendored Play API document states it; the engine accepts only that encoding. Published: the canonical encoding is implemented by `signing`'s `encodeTypedData` and pinned by the vendored `typed-data/` vectors ([The cryptography](./client-kit/the-cryptography.md)).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| the backend's rejections and their stable error codes                       | A refused action changes nothing. The player sees `INVALID_ARGUMENT` (400) for a malformed, wrongly typed, unsigned, non-canonical, wrongly signed, or illegal action. The Play API document answers a move or a cash-out signed for a state the round has left (another action at a sequence already accepted, or a wrong `sequence` or `previous`) with a 409 `STALE_ACTION`; a stale cancel is a 400 `INVALID_ARGUMENT`, and a cancel never answers 409. W-19 handles both codes alike. A repeated move or cash-out is answered from the request log; a cancel never is, and a repeat of an accepted cancel is a 422 `FAILED_PRECONDITION`. The kit's rules follow them: after a 400 or a 409 to a signed move or cash-out, the shell reads the Snapshot before it signs anything else for the round (W-19), and after a lost send of a cancel (no answer, or a 503 not marked `retryable: false`) it reads the Snapshot before it sends the same cancel again (W-16, W-25).                                                                                                       |

The shell rules restated in this spec (so the Wrapper can be reviewed without
the signed-action spec): never sign two actions at one sequence; track `T_n`;
build the canonical action from the game's request; sign a cash-out only when
the player asks for it (W-24); check the bind and the tip before the first
signature; canonical signatures only.

## Decided questions

OQ-1 to OQ-6 were decided by the TPO on 2026-10-15, and OQ-7 on 2026-10-16. OQ-8
was decided on 2026-10-16 by the backend's player-facing contract, as the
backend team stated it. Each row keeps the question, the options, and the
decision. The spec follows the decision.

| OQ-1 | **Storage that survives a reload.** The first-release acceptance criteria forbid a key or token in "storage that survives the session". An earlier design note asked for the key to be kept in persistent storage for the session's lifetime, so a reload could continue the round. Both cannot hold, and the backend does not hand an open round to a new session. | (A) memory only; a reload forfeits the round by its expiry rule. (B) `sessionStorage`, which survives a reload and is copied by a duplicated tab.
